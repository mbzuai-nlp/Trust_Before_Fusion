# MM-Mirage Image Pollution Methods

7 attack types, 2 records each → **14 polluted records per question**.

---

## T1 — Caption Flip

**Goal:** Replace the image's associated text with a false caption while leaving the image URL unchanged. The visual content is unmodified; only the metadata is poisoned.

**Mechanism:**
- A single Gemini 2.5 Flash text call generates all Gemini-backed metadata for a question in one shot: 2 false captions, a FIGSTEP claim, a REWRITE instruction, and a CLIP concept.
- False captions are prompted to contain a specific factual error (wrong location, name, or date) and stay under 10 words.
- The original `image_url` is kept; `polluted_image_path` is null (no saved file).

**Model:** `gemini-2.5-flash` (text only)

---

## T2 — Entity Swap

**Goal:** Replace the image URL with a visually unrelated image from a different question in the same dataset, creating a subject/image mismatch.

**Mechanism:**
- A partner question is selected whose subject differs from the current question's subject.
- The partner's `image_url` replaces the current record's URL — no image download or modification required.
- Partners are shuffled per question so T2 record 0 and record 1 use different donors.

**Cost:** Near-zero — no network calls, no compute.

---

## T3 — Semantic Entity Rewrite

**Goal:** Produce a visually edited image that changes scene elements (background, objects, environment) while preserving the main subject, making the visual context factually misleading.

**Mechanism:**
- The merged Gemini text call produces a `REWRITE` instruction in the form `"change [element] to [false element]"`.
- The original image and instruction are sent to `models/gemini-2.5-flash-image` (Gemini's image editing endpoint).
- Up to 3 prompt fallbacks: specific instruction → environmental shift to dusk → global colour grade.
- If all API attempts fail, a local PIL fallback applies a tinted colour gradient overlay with random contrast/saturation shifts.
- Both T3 records are submitted as **parallel futures** so both Gemini edit calls run concurrently.

**Model:** `models/gemini-2.5-flash-image`  
**Fallback:** PIL tint + contrast/saturation jitter

---

## T4 — FigStep Typography

**Goal:** Inject a false factual claim directly into the image as rendered text, simulating the FigStep jailbreak-style typography attack on vision-language models.

**Mechanism — Style 0 (Caption Bar):**
- A dark semi-transparent bar (`rgba(15,15,15,215)`) is composited onto the bottom of the image.
- Bar height grows dynamically: `bar_h = max(56, n_lines × line_height + 2 × padding)`.
- The false claim is word-wrapped via `textlength()` measurement to fill the full image width at font size `max(14, height/28)`.
- A 3px red accent line (`rgba(200,50,50,230)`) runs along the top edge of the bar.

**Mechanism — Style 1 (Diagonal Watermark):**
- The claim is tiled across a 2× canvas at 30° rotation, `rgba(255,255,255,55)` opacity.
- Tile spacing: `(text_width + 60) × (text_height + 40)`, alternating rows offset by half-step.

**The FIGSTEP claim** is generated by the merged Gemini text call with a prompt requiring it to directly answer the question with a specific factual error (10–14 words, declarative, no hedging).

**Library:** PIL / Pillow only — no model inference

---

## T5 — Adversarial Patch (PGD)

**Goal:** Embed an imperceptible or semi-visible adversarial patch that steers CLIP's image embedding toward a false concept, causing CLIP-based retrievers to misidentify the image.

**Mechanism:**
- Image resized to `512×512`.
- A random patch of size `√(PATCH_FRAC × H × W)` pixels (≈10% area) is placed in the top-right corner `(py=10, px=W−side−10)`.
- **PGD loop** (20 steps, `α = 2/255`, `ε` unconstrained per-step):
  - Patch inserted into canvas; canvas passed through CLIP ViT-L/14 image encoder.
  - Loss = negative cosine similarity between image embedding and the text embedding of the false `CLIP_CONCEPT`.
  - Gradient sign step: `patch ← patch − α × sign(∇patch)`, clamped to `[0, 1]`.
- Patch is composited back; result returned at original resolution.

**Model:** `openai/clip-vit-large-patch14` via HuggingFace  
**Device:** MPS (Apple Silicon GPU) or CPU  
**Runs on GPU worker thread** to avoid concurrent MPS access

---

## T6 — Image Blend

**Goal:** Overlay a visually confusing donor image onto the original, creating a composite that mixes two unrelated subjects.

**Mechanism:**
- An Ollama VLM (`gemma3:4b-it-qat`) describes the source image in one short phrase (used as prompt metadata).
- A donor question is selected via the partner map (different subject, different donor per record).
- The donor image is resized to 45% of the original's dimensions and alpha-composited centered on the original at **75% opacity**.
- A 3px red border (`rgba(220,30,30,255)`) is drawn around the donor overlay to accentuate the intrusion.
- If Ollama is unavailable, the VLM description is empty but the blend still proceeds.

**Model:** `gemma3:4b-it-qat` via Ollama (optional, graceful fallback)  
**Library:** PIL alpha composite

---

## T7 — Neural Style Transfer (NST)

**Goal:** Transfer the visual texture and style of a donor image onto the content of the source image using Gram-matrix optimization, producing a stylistically alien but semantically confusing result.

**Mechanism:**
- Both images resized to `256×256` for speed.
- **Style grams** computed from the frozen VGG-19 encoder at layers `relu1_1, relu2_1, relu3_1, relu4_1` (indices 1, 6, 11, 20 of the feature sequence) with no content loss — pure style transfer.
- Optimization variable `opt` initialized from the content image (warm start for fast convergence).
- **Adam loop** (15 steps, `lr = 0.02`, style weight `5×10⁵`):
  - Forward: `opt` → VGG → Gram matrices → MSE loss vs. style grams.
  - Backward: autograd through frozen VGG (inplace ReLUs disabled to allow backprop).
  - `opt` clamped to `[0, 1]` in-place after each step to prevent pixel drift.
- Output resized back to original dimensions via LANCZOS.

**Model:** `torchvision.models.vgg19` (pretrained, frozen, encoder-only — no decoder needed)  
**Device:** MPS (Apple Silicon GPU) or CPU  
**Runs on GPU worker thread** (same singleton queue as T5)

---

## Parallelism & Execution Order

```
Worker thread (per question):
  ├── T1/T2  — instant (text/URL only)
  ├── T5 ×2  ──┐ submitted to GPU queue (async)
  ├── T7 ×2  ──┤ submitted to GPU queue (async)
  ├── T3 ×2  ──┤ parallel Gemini image-edit futures
  ├── T4 ×2  ──┤ PIL only (instant)
  ├── T6 ×2  ──┘ Ollama VLM + PIL
  └── collect T5/T7 GPU results (block until GPU done)
```

`N_WORKERS=3` question workers run concurrently. All GPU ops are serialized through a single background thread to avoid MPS contention.
